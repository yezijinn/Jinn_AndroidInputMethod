# 隐蔽缺陷挖掘指南：为什么"功能正常"最危险

以 CapsWriterIME 词库模块六轮审查为样本整理。
生成时间：2026-09-15

---

## 一、这类缺陷的共同特征

**它们全部满足：功能测试通过、无崩溃、无异常日志、用户不会主动报障。**

于是常规审查的三道防线同时失效：

| 常规手段 | 为何拦不住 |
|---|---|
| **功能测试** | 功能确实是对的 —— 候选能出来、能上屏、词库能加载 |
| **崩溃监控** | 不崩溃。最严重的一类连异常都不抛 |
| **日志排查** | 要么没有日志，要么日志本身就没被执行到 |
| **代码走查** | 单看一段代码"逻辑正确"，问题出在**跨模块的时序/并发/语义**上 |
| **用户反馈** | 用户以为"输入法就这样"，或干脆不用那个功能 |

**一句话**：这类缺陷的判据不是"能不能用"，而是**"在什么条件下会不成立"**。

## 二、七类藏匿形态（附本项目实例）

### 类型 1：静默失败 —— 失败了但没人知道

**为何漏检**：没有异常、没有日志、界面照常。失败路径被 `runCatching` 兜住后
只打一条 V 级日志（默认不落盘），等于没打。

**藏匿位置**：`try/catch`、`runCatching`、`onFailure { }` 的分支里；
后台线程的顶层；初始化路径。

**触发条件**：依赖项异常（文件损坏、权限、存储故障）；网络失败。

**本项目实例**：
```kotlin
// 第四轮发现：JinnIme.onCreate
Thread { PinyinEngine.load(this) }.start()   // 裸线程，无 try/catch
```
基础包解压一旦抛异常 → 穿透到线程外 → **线程静默死亡** →
`loaded` 永远 false → **打字没有任何候选**，而且「加载完成」「内存采样」
这些日志**全都执行不到** —— 排查时零线索。

**排查思路**：**逐个失败分支问三个问题**
1. 这里失败，用户看到什么？（如果"什么都看不出来" → 中招）
2. 日志里能看出失败吗？（如果日志在失败行**之后**才打 → 中招）
3. 失败后会重试吗？会的话重试条件成立吗？

### 类型 2：性能退化 —— 正确但昂贵

**为何漏检**：功能完全正确，只是慢。没有性能基线就没有异常；
开发者机器快，低端机才暴露。

**藏匿位置**：循环内创建对象、每次刷新全量重建、无上限的集合渲染、
主线程 IO。

**触发条件**：数据量放大；低端机；**高频操作路径**（每次按键都走）。

**本项目实例**：
```kotlin
// 第六轮发现：PinyinKeyboardView.refreshCandidateBar
for ((index, candidate) in result.candidates.withIndex()) {  // ← 无上限
    val item = TextView(context)                            // ← 每条一个 View
}
```
候选可达 **60 条**（真实单字表：`yi` 326 字、平均 42.3 字/音节），
而这里**每次按键全量重建** → 一次按键创建 60 个 View。

**排查思路**：**把定性换成定量**
- 不要停在"可能慢"，要算出"60 个 View / 每次按键"
- 反问：这个循环的**上界**是多少？上界**由谁决定**（常量还是数据）？
- 关键：**上界是常量也要看它常不常被打满** —— 60 这个上限"经常打满"才是问题

---

### 类型 3：状态陈旧 —— 改了一处漏了另一处

**为何漏检**：新增字段时只改了主要逻辑，忘记同步"清理/复位/重置"路径。
表现是"偶尔不对"，难复现。

**藏匿位置**：`reset*()`、`clear*()`、`invalidate*()`、`reload*()`、
测试的 `@Before`、状态机的所有出口。

**触发条件**：切换场景、重新加载、测试类连续执行（状态跨用例污染）。

**本项目实例**：
```kotlin
// 新增延迟加载状态时，resetForTest 起初没有复位它们
optionalLoaded / optionalLoading
```
→ 下一个测试类会**误判可选包已加载**，用例互相污染。

**排查思路**：**新增字段时，反向搜索所有"状态清理点"**
```bash
grep -n "\.clear()\|= null\|= false\|= emptyList()" <文件>
```
逐个核对：这个新字段是否**也该在这里复位**？

---

### 类型 4：生命周期错配 —— 只在特定时序出问题

**为何漏检**：需要精确的时序（先关页面再回调、先销毁再延时）。
手工测试很难踩中，静态看代码也"没毛病"。

**藏匿位置**：`runOnUiThread`、`postDelayed`、回调、异步任务完成分支。

**触发条件**：用户在操作完成前退出/切换页面；配置变更（旋转）。

**本项目实例**（两个都出在同一个页面）：
```kotlin
// 第二轮发现一：页面已关闭，回调仍操作 UI
runOnUiThread { setStatus(...); refreshList() }   // ← 无 isFinishing 检查

// 第二轮发现二：延时任务挂在 View 上
listHost.postDelayed({ killProcess(myPid()) }, 1500)  // ← View 销毁后不保证执行
```
第二个尤其隐蔽：**下载成功了却没生效，而且没有任何提示**。

**排查思路**：**对每个异步完成点问**
1. 回调执行时，宿主还活着吗？（Activity → `isFinishing/isDestroyed`）
2. 这个延时/回调**挂在谁身上**？（View 会随页面销毁 → 改挂 `Handler`）
3. 宿主死了，**业务副作用还需要完成吗**？（需要的话，与 UI 更新**分开**）

---

### 类型 5：并发竞态 —— 窗口窄，靠运气

**为何漏检**：需要两个线程在同一时刻命中同一份数据。开发时往往"刚好没撞上"，
上线后偶发、无法复现。

**藏匿位置**：**后台加载 × 前台查询**共存处；状态标志；缓存；
非线程安全容器（`HashMap`/`ArrayList`/`HashSet`）。

**触发条件**：后台任务与用户操作**时间重叠**（尤其是"延迟 N 秒后加载"这类设计，
必然与用户活跃期重叠）。

**本项目实例**：
```kotlin
// 第一轮发现：延迟加载在后台 merge 词库，用户此刻正在打字
phrasesByPinyin[pinyin] = existing + kept    // 后台写
phrasesByPinyin[key]                          // 主线程读（query）
// 容器是普通 HashMap → 扩容期桶链表成环 → 读方死循环，IME 卡死
```
**注意因果链**：这个缺陷是**引入"延迟加载"时带出来的** ——
原本加载集中在一处，没有并发；改成分散后，隐患才出现。

**排查思路**：
1. **列出所有"后台写"的字段**，逐一确认主线程是否读它
2. 容器：`HashMap`→`ConcurrentHashMap`；有序表→**不可变快照 + 整体替换引用**
   （原地 `clear()+addAll()` 会让读方看到中间态）
3. 状态标志：跨线程读写的都要 `@Volatile`
4. **凡是有"延迟/后台加载"设计，一律按并发场景审**

### 类型 6：语义偏移 —— 代码对，但意思不对

**为何漏检**：代码逻辑自洽，能跑通，只是**不符合业务语义**。
需要理解"应该是什么"才看得出来。

**藏匿位置**：映射/索引的构建（`putIfAbsent` vs `put`）、
默认值选择、单位/量纲、边界包含性（`<` vs `<=`）。

**触发条件**：多值场景（多音字、多标签）；只有部分数据受影响。

**本项目实例**：
```kotlin
// 第三轮发现：wordToPinyin.putIfAbsent(word, pinyin)
// 一个词有多个拼音键时（多音字，全库 2,065 个）只记首个
// → predict() 只能沿一个键查找，预测结果不全
```
评估后**不修**（占比 0.1%、预测是辅助功能、改动牵动所有调用点）。

**排查思路**：**问"这个数据结构能表达全部信息吗"**
- `Map<K, V>` 用在"一个 K 可能对应多个 V"的场景 → 语义已丢失
- 出现 `putIfAbsent` / `firstOrNull` / `take(1)` 的地方，都要问**丢了什么**

---

### 类型 7：测试盲区 —— 想测却测不到

**为何漏检**：不是"忘了写测试"，而是**测试入口从设计上够不到那个分支**，
于是形成了"看起来有测试、实际没覆盖"的假象。

**藏匿位置**：测试注入接口（如 `loadFromTexts`）、依赖注入点、
硬编码的测试替身。

**触发条件**：给模块加了新分支（新语义、新参数），但没同步扩展测试入口。

**本项目实例**：
```kotlin
// 第五轮发现
fun loadFromTexts(...) { loadPhrasesText(phrases) }        // merge 恒为 false
private fun loadPhrasesText(text: String)                  // private，无 merge 参数
```
→ 第一轮修的"合并去重"**从设计上就无法被测试**，长期没有回归防线。

**排查思路**：**给模块加新分支时，立刻检查"测试能构造到它吗"**
- 生产代码里的 `private` 注入方法，往往就是盲区的入口
- 判定标准：把新分支的**每个参数**都试着从测试侧传一次，传不进去就是盲区

## 三、最高效的排查思路（按性价比排序）

### ① 不变式检验 —— 投入产出比最高

**不问"功能对不对"，问"有没有什么是永远该成立的"**：

| 不变式 | 违反即缺陷 |
|---|---|
| 候选列表无重复 | 去重缺失 |
| 已加载 == 可查询 | 加载/索引不同步 |
| 内存不随操作次数增长 | 泄漏/无界缓存 |
| 键集合 ⊇ 值集合（反向索引一致）| 索引构建漏项 |
| 数量关系守恒（进 == 出 + 丢）| 静默丢弃 |

**验证方式**：**全量数据扫描**（不是抽样）。本项目第三轮用这招一次性
定位了「跨键重复 2,068 词 → 实为多音字，非缺陷」，比读代码快得多。

### ② 量化替代定性 —— 把"可能"变成数字

- ✗「候选可能比较多」 → ✓「最多 60 条，且 93 个音节会打满」
- ✗「加载可能慢」 → ✓「172 万键耗时 25.4 秒，其中 18 万键的扩展包占 8 秒」

**方法**：用真实数据统计上界分布，而不是看代码里的常量。
**常量上限 ≠ 实际常见值** —— 要问"这个上限被打满的频率"。

### ③ 极端化输入 —— 把参数推到边界

| 维度 | 推到极端 |
|---|---|
| 规模 | 空 / 1 条 / 巨量 |
| 时长 | 立即 / 极长 |
| 时序 | 操作未完成就退出 |
| 内容 | 全角/生僻字/超长串/特殊字符 |

### ④ 故障注入 —— 假装依赖坏了

- 切断网络 → 看下载失败路径
- 塞损坏文件 → 看加载容错
- 拔掉存储权限 → 看降级行为

**看两件事**：① 有没有留痕（日志/提示）② 有没有降级（部分可用）

### ⑤ 对照法 —— 找出"应该同步却不同步"的地方

**列出所有"新增 X 时要同步改 Y"的关系**，然后反向搜索：

| 新增 | 必须同步 |
|---|---|
| 状态字段 | `reset*` / `clear*` |
| 容器 | 线程安全策略 |
| 分支/参数 | 测试注入入口 |
| 资源 | `use {}` 关闭 |
| 下载的包 | Release 附件 + 下载源 URL |

## 四、验证方式的选择原则

| 缺陷类型 | 最佳验证 | 次优 |
|---|---|---|
| 静默失败 | **故障注入 + 看日志有无痕迹** | 代码审查失败分支 |
| 性能退化 | **真实数据统计上界 + 真机计时** | 单测打印量级 |
| 状态陈旧 | **连续执行两个用例，看后者是否受污染** | 反向搜索清理点 |
| 生命周期 | **真机按真实时序操作**（边下载边退出）| 代码审查异步完成点 |
| 并发竞态 | **构造重叠窗口**（后台加载时连续打字）| 静态审查容器类型 |
| 语义偏移 | **全量数据重算**（如重新统计多音字）| 单测覆盖多值场景 |
| 测试盲区 | **试着从测试侧传每个新参数** | 审查 `private` 注入方法 |

**共同原则**：**先用最便宜的静态扫描定位嫌疑，再用最贴近真实的验证确认，最后留一条不易失效的回归防线**（纯函数断言 / 不变式测试 / 数量关系断言）。

## 五、给审查者的三条经验

1. **缺陷高发于"后加的改动"**：本项目 6 轮里，最严重的问题全都出在
   **新增的时序逻辑**上（延迟加载带出并发、分类页带出生命周期）。
   审查时应优先看 **diff**，而不是看全量代码。

2. **"功能正常"不是通过标准**：真正的判据是
   **"在什么条件下会不成立"** —— 把每个假设都写成"若 X 不成立会怎样"。

3. **留防线比修一次更重要**：静默失败、性能退化、状态陈旧这三类**都会复发**。
   修完必须留一条**不易失效的断言**（如"候选数可达 60，渲染必须截断"这类
   锁定事实的测试），否则下次改动又会悄悄退化回去。
