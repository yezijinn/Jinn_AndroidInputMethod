==================================================
二、最重要的安全原则
==================================================

必须明确区分两个概念：

A. Android 系统剪贴板

由 Android Framework / ClipboardManager 管理。

B. 本输入法自己的剪贴板历史

由本项目自己管理。

本项目可以完全控制：

“自己的剪贴板历史”。

但普通 Android 输入法 APP 无法仅凭自身权限，强制禁止其他 APP 通过 Android 系统 ClipboardManager 读取系统剪贴板。

因此：

【绝对不要实现一个虚假的“系统级阻止其他 APP 读取 ClipboardManager”功能。】

不要声称：

“任何未经授权的 APP 都绝对无法读取 Android 系统剪贴板”。

普通应用无法提供这种系统级保证。

真正能够由本项目严格控制的是：

【本输入法自己的剪贴板历史数据库，以及本项目提供给第三方 APP 的访问接口。】

==================================================
三、整体架构
==================================================

设计为：

Android System Clipboard
        ↓
ClipboardManager
        ↓
Clipboard Observer
        ↓
本输入法 Clipboard Manager
        ↓
敏感内容检测
        ↓
保存策略判断
        ↓
加密
        ↓
本地 Clipboard History Database
        ↓
┌─────────────────────┐
│                     │
↓                     ↓
输入法剪贴板 UI       第三方 APP 受控访问接口
                         ↓
                     包名权限检查
                         ↓
                 授权 / 拒绝
                         ↓
                 最多返回 3 条

==================================================
四、默认权限策略
==================================================

默认策略：

1. 其他 APP 可以按照 Android 系统机制向系统剪贴板写入内容。

2. 本输入法默认不主动读取其他 APP 的剪贴板内容。

3. 本输入法只有在符合 Android 系统 API、系统版本限制和用户设置的情况下，才读取系统剪贴板。

4. 其他 APP 是否能够直接读取 Android 系统 ClipboardManager，不由本输入法控制。

5. 本项目提供的“剪贴板历史访问接口”默认禁止所有第三方 APP。

6. 用户可以主动授权指定 APP。

==================================================
五、第三方 APP 授权机制
==================================================

建立一个：

“剪贴板历史访问权限管理”

用户可以看到可识别的 APP，并按照包名授权。

例如：

com.example.app1
允许读取：是

com.example.app2
允许读取：否

com.example.app3
允许读取：否

默认：

所有第三方 APP：

读取本输入法剪贴板历史 = 禁止

用户主动授权后：

指定 APP：

读取本输入法剪贴板历史 = 允许

==================================================
六、第三方 APP 最大读取数量
==================================================

即使用户授权：

第三方 APP 每次通过本项目提供的接口：

最多只能读取最新 3 条剪贴板历史。

例如：

历史：

1. A
2. B
3. C
4. D
5. E

第三方 APP 最多获得：

A
B
C

无法通过：

分页
重复请求
offset
limit
多次 API 请求
并发请求

获取第 4、5 条以及更早的数据。

也就是说：

【“最多 3 条”是权限本身的一部分，而不是 UI 层面的限制。】

服务端/Provider/API 层必须强制限制。

==================================================
七、包名安全
==================================================

第三方 APP 授权必须绑定：

packageName

不要只使用 APP 名称。

例如：

com.example.app

权限数据库保存：

package_name
app_name
allowed
created_at
updated_at

如果 APP 名称发生变化：

权限仍然根据 packageName 判断。

如果 APP 被卸载：

可以自动删除对应授权记录。

如果重新安装：

默认视为新的 APP，不能自动继承旧授权。

==================================================
八、第三方访问接口
==================================================

如果使用：

ContentProvider
Bound Service
Binder
AIDL
其他 Android IPC

必须选择最安全、最适合当前项目的方案。

重点原则：

【未授权 APP 无法通过本项目提供的 IPC 接口获取剪贴板历史。】

访问流程：

第三方 APP
    ↓
请求 Clipboard History
    ↓
系统识别调用方 UID
    ↓
获取 packageName
    ↓
检查授权
    ↓
检查是否属于授权 APP
    ↓
限制最大返回 3 条
    ↓
返回允许的数据

不要让第三方 APP 自己提交一个 packageName：

packageName=com.example.app

然后系统就相信它。

必须从 Android Binder / IPC 调用身份获取真实调用方身份。

==================================================
九、权限绕过防护
==================================================

重点防止：

1. 修改请求中的 packageName
2. offset 分页
3. limit 修改
4. 重复请求
5. 并发请求
6. SQL 注入
7. 通过 ContentProvider projection 获取隐藏字段
8. 通过 URI 越权访问
9. 通过 debug 接口访问
10. 导出未保护的 Activity
11. 导出未保护的 Service
12. 导出未保护的 Provider
13. 通过 Intent 绕过权限
14. 通过备份文件直接读取历史
15. 通过日志读取剪贴板明文

所有第三方访问入口必须统一经过权限检查。

==================================================
十、加密存储
==================================================

剪贴板历史不能以明文形式存储在普通文件中。

禁止：

明文 TXT
明文 JSON
明文 SQLite
SharedPreferences 明文
普通缓存文件明文
日志明文

推荐：

Android Keystore
+
AES-256-GCM

设计：

明文 Clipboard Content
        ↓
AES-256-GCM
        ↓
Encrypted Database

加密密钥：

必须通过 Android Keystore 管理。

禁止：

1. 把密钥写死在代码里
2. 把密钥放 SharedPreferences
3. 把密钥放普通文件
4. 把密钥直接写进数据库
5. 自己设计加密算法

不要自行发明密码算法。

==================================================
十一、内存中的明文
==================================================

磁盘加密并不意味着完全安全。

程序运行时：

密文
 ↓
解密
 ↓
内存中的明文

因此：

【不要在程序启动时一次性解密全部剪贴板历史。】

必须采用：

按需解密
按需加载

例如用户打开剪贴板：

只解密当前需要显示的数据。

搜索时：

尽可能设计专用搜索索引。

不允许无意义地：

一次性解密 9999 条历史内容。

十二、敏感内容检测

- 验证码

- 银行卡号码
- API Key

- Cookie
- JWT
- 私钥
- 密钥

必须设计：

Sensitive Content Detector

第一版可以使用规则匹配。

例如：

验证码
银行卡号
JWT
API Key
常见 Token 格式

检测到敏感内容后：

默认不进入长期历史。

建议策略：

敏感内容：
默认不保存

或者：

敏感内容：
临时保存
自动过期

必须在设置中明确显示该策略。

性能
