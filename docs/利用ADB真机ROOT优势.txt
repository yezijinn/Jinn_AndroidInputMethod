你这个场景有 **ADB + Root + KernelSU 真机**，可以把调试体系做得比普通 Android 项目完整很多。重点不是“多打几条 Log”，而是建立一套**可追踪、可复现、可自动采集、可对比、可诊断**的工程化调试系统。

## 1. 建立统一 Debug Telemetry

建议把现在的 `Diagnostics.kt` 升级成项目级诊断中心：

```text
Diagnostics
├── Logcat
├── 文件日志
├── Crash 捕获
├── Thread/Looper 信息
├── Activity/IME 生命周期
├── View/Layout 状态
├── IPC/WebSocket
├── Clipboard
├── Pinyin
├── Audio
├── Root/Shizuku
├── Permission
└── Performance
```

所有模块禁止：

```kotlin
println()
Log.d(...)
Log.e(...)
```

统一：

```kotlin
Diagnostics.d(TAG, "...")
Diagnostics.i(TAG, "...")
Diagnostics.w(TAG, "...")
Diagnostics.e(TAG, "...")
```

这样以后可以**全局控制日志级别**。

---

# 2. 每条日志必须具备上下文

不要：

```text
剪贴板打开
```

应该：

```text
[Clipboard][OPEN] panel=clipboard thread=main
[Clipboard][DB] allSize=8 thread=DefaultDispatcher-worker-1
[Clipboard][FILTER] category=ALL visibleSize=8 thread=main
[Clipboard][ADAPTER] count=8 thread=main
```

建议统一格式：

```text
时间
PID
线程
TAG
模块
事件
关键参数
```

例如：

```text
12:31:42.153 pid=18421 tid=main
[JinnClipboard][REFRESH]
category=ALL allSize=8 visibleSize=8 adapterCount=8
```

**绝对不要记录密码、剪贴板正文、语音识别正文等敏感数据。**

---

# 3. 给关键流程建立 Trace ID

这是非常值得加的。

一次操作生成：

```text
traceId=CLIP-8F31
```

然后整个流程：

```text
CLIP-8F31 OPEN
CLIP-8F31 REFRESH
CLIP-8F31 DB
CLIP-8F31 FILTER
CLIP-8F31 ADAPTER
CLIP-8F31 RENDER
```

以后你从 5000 行日志里面搜索：

```text
CLIP-8F31
```

就能得到完整调用链。

不仅剪贴板可以用：

```text
IME-xxxx
ASR-xxxx
PINYIN-xxxx
ROOT-xxxx
```

# 4. 给每个核心模块增加 State Snapshot

例如 `JinnIme`：

IME State
├── inputStarted
├── inputViewStarted
├── windowShown
├── currentPanel
├── keyboardMode
├── connectionState

出现 BUG 时输出：

```text
[IME][STATE]
windowShown=true
inputStarted=true
panel=CLIPBOARD
keyboardMode=PINYIN
inputConnection=true
```

剪贴板：

```text
[CLIPBOARD][STATE]
category=ALL
allSize=8
visibleSize=8
adapterCount=8
selectedIndex=-1
```

这样比单纯 Logcat 有价值很多。

# 5. 建立“诊断快照”功能

这是 Root + ADB 最大的优势之一。

增加：

```text
Settings
→ 开发者/诊断
→ 导出诊断包
```

自动收集：

```text
diagnostics/
├── app.log
├── crash.log
├── ime.log
├── clipboard.log
├── asr.log
├── pinyin.log
├── lifecycle.log
├── dumpsys_input_method.txt
├── dumpsys_window.txt
├── dumpsys_activity.txt
├── dumpsys_meminfo.txt
├── dumpsys_cpuinfo.txt
├── package_info.txt
├── permissions.txt
├── appops.txt
└── root_status.txt
```

最后生成：

```text
JinnIme-Diagnostics-20260816-113025.zip
```

以后出现 BUG，基本可以做到：

> 复现 → 点一次“导出诊断” → 整包分析。

# 6. Root 用来获取普通 App 拿不到的系统状态

你的手机有 Root，这一点应该充分利用。

例如：

```powershell
adb shell su -c "dumpsys input_method"
```

```powershell
adb shell su -c "dumpsys window"
```

```powershell
adb shell su -c "dumpsys activity"
```

```powershell
adb shell su -c "dumpsys meminfo com.jinn.voiceinput"
```

```powershell
adb shell su -c "dumpsys cpuinfo"
```

```powershell
adb shell su -c "appops get com.jinn.voiceinput"
```

```powershell
adb shell su -c "dumpsys package com.jinn.voiceinput"
```

这样你可以同时获得：

```text
应用内部状态
+
Android Framework 状态
+
IME 状态
+
Window 状态
+
权限状态
+
进程状态
```

这是普通用户环境很难做到的。

# 8. 增加 ANR / Crash / Native Crash 监控

不仅捕获 Java/Kotlin Exception。

还应该检查：

```text
Crash
ANR
Native Crash
OOM
StrictMode
```

Root 下可以进一步查看：

```powershell
adb shell su -c "ls -lt /data/anr/"
```

```powershell
adb shell su -c "ls -lt /data/tombstones/"
```

这样如果输入法：

```text
卡死
闪退
ANR
Native crash
```

可以直接把系统级证据拿出来。

# 9. 开发版本开启 StrictMode

Debug Build 开启：

```kotlin
StrictMode.enableDefaults()
```

进一步可以检测：

```text
主线程磁盘 IO
主线程网络
资源泄漏
慢操作
```

这对你的输入法特别重要。

因为 IME 要求：

```text
UI Thread
        ↓
极低延迟
```

不能出现：

```text
主线程加载词库
主线程数据库查询
主线程文件 IO
主线程 WebSocket 阻塞
```

# 10. 给耗时操作统一打点

不要只记录：

```text
词库加载完成
```

应该：

```text
[Pinyin][LOAD] start
[Pinyin][LOAD] read=1823ms
[Pinyin][LOAD] parse=423ms
[Pinyin][LOAD] buildIndex=381ms
[Pinyin][LOAD] total=2627ms
```

ASR：

```text
[ASR][TASK] begin
[ASR][TASK] firstAudio
[ASR][TASK] firstResult
[ASR][TASK] final
[ASR][TASK] total=xxxxms
```

剪贴板：

```text
[Clipboard][REFRESH] db=12ms
[Clipboard][FILTER]=1ms
[Clipboard][ADAPTER]=2ms
```

这样以后优化性能非常方便。

# 11. 建立“模块级 Debug 开关”

例如：

```text
Diagnostics

```

Logcat 不会被几千条 ASR/录音日志淹没。

# 12. 最重要：增加“事件序列”

对于你这种 IME，很多 BUG 是时序 BUG：

```text
A → B → C → D → A
```

因此建议维护一个内存 Ring Buffer：

```text
最近 500 个事件
```

例如：

```text
11:30:01.001 onStartInput
11:30:01.032 onStartInputView
11:30:01.041 onWindowShown
11:30:01.122 ClipboardOpen
11:30:01.130 ClipboardRefresh
11:30:01.151 ViewInvisible
11:30:01.170 WindowHidden
11:30:01.681 WindowShown
```

即使没有及时打开 Logcat，发生 BUG 后也能看到**BUG 前几秒发生了什么**。

这对你之前的：

> 键盘自动收起 → 自动唤醒 → 循环

特别有价值。

---

# 13. Root 下增加 Watchdog

Debug 版本可以有一个：

```text
JinnIme Watchdog
```

检测：

```text
IME 是否运行
进程是否存在
InputMethod 是否当前激活
Window 是否显示
```

**注意：Watchdog 只记录，不要自动修复。**

否则：

```text
BUG
→ Watchdog 修复
→ 又产生 BUG
→ 无限循环
```

你之前的“收起 → 唤醒”问题就是典型例子。

Debug 阶段应该：

```text
检测异常
↓
记录
↓
保留现场
```

而不是：

```text
检测异常
↓
强行恢复
```

# 14. 最终推荐架构

```text
                    ┌──────────────┐
                    │  Diagnostics │
                    └──────┬───────┘
                           │
       ┌──────────┬────────┼────────┬──────────┐
       ↓          ↓        ↓        ↓          ↓
      IME       Clipboard  ASR     Pinyin     Root
       │          │        │        │          │
       └──────────┴────────┼────────┴──────────┘
                           ↓
                    Event / Trace
                           ↓
              ┌────────────┴────────────┐
              ↓                         ↓
          Logcat                   File Log
              │                         │
              └────────────┬────────────┘
                           ↓
                    Diagnostic ZIP
                           ↑
                           │
                         ADB
                           │
                         ROOT
                           │
                    Android Framework
```

## 你这个项目最值得优先做的 6 项

按收益排序：

| 优先级 | 功能 | 价值 |
|---|---|---|
| **P0** | 统一 `Diagnostics` | 所有 BUG 的基础 |
| **P0** | Trace ID + Event 序列 | 定位时序 BUG |
| **P0** | `dumpsys input_method/window` 自动采集 | 专门解决 IME BUG |
| **P1** | 一键 Diagnostic ZIP | 大幅降低复现/反馈成本 |
| **P1** | Debug 模块开关 | 避免日志污染 |
| **P1** | StrictMode + 性能打点 | 查卡顿、耗电、主线程问题 |

尤其建议你把**“一键诊断包 + Ring Buffer 事件记录 + ADB/Root 系统快照”**作为这个项目的标准调试基础设施。这样以后 AI Agent 查 BUG 时，你直接把诊断包交给它，它可以同时分析**代码日志、运行时状态和 Android 系统状态**，比单纯 `adb logcat` 高效得多。
